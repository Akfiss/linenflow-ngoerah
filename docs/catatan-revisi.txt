Yang Sudah Oke Banget (Keep It!)
central_stocks vs room_stocks: Pemisahan ini cerdas. Laundry punya state (Kotor/Cuci/Bersih), sedangkan ruangan cuma butuh tahu "Ada berapa barang di sini?".

Transaction Types: Enum OUT_DISTRIBUTION, WASH_START, dll sudah meng-cover siklus hidup linen.

Nullable room_id di Transaksi: Ini life-saver. Saat proses cuci (Internal Laundry), kita nggak butuh ID ruangan. Desain ini fleksibel.

2. Soft Deletes (Penting untuk Audit)
Di Rumah Sakit, data haram hukumnya dihapus permanen. Bayangkan kalau ada selisih stok, tapi user yang input sudah dihapus? Bahaya.

Saran: Tambahkan kolom deleted_at (timestamp, nullable) di tabel users, linens, dan rooms. Gunakan fitur SoftDeletes di Model Laravel.

3. Catatan Masalah "Lifespan Cycles" (Siklus Cuci)
Di tabel LINENS kamu ada lifespan_cycles. Ini bagus untuk referensi pabrik. TAPI, karena sistem ini Bulk Tracking (jumlah) dan bukan Item Tracking (per lembar pakai RFID/Barcode unik), kamu tidak akan bisa melacak umur sprei secara spesifik.

Masalah: Kamu punya 100 sprei. 50 baru beli kemarin, 50 beli tahun lalu. Semuanya kode SKU sama. Saat dicuci, sistem nggak tahu mana yang sprei baru, mana yang lama.

Solusi: Kolom lifespan_cycles tetap simpan saja sebagai data referensi (misal: "Sprei ini harusnya rusak setelah 100x cuci"). Nanti di laporan, kamu bisa pakai estimasi turnover rate.

4. Kunci Integritas Stok (Mencegah Minus)
Di level database (Migration), pastikan stok tidak bisa minus dengan Unsigned Integer atau constraint, tapi karena kadang ada adjustment, validasi logic di Laravel Service lebih krusial.

Selanjutnya Menentukan Role & Permission (Hak Akses) sebelum mulai coding adalah langkah krusial. Ini yang membedakan aplikasi "asal jalan" dengan aplikasi enterprise yang aman.

Di lingkungan Rumah Sakit besar (seperti RS Sanglah), hierarki itu ketat. Kita tidak boleh membiarkan staf biasa mengubah Master Data, dan kita tidak boleh membiarkan perawat di satu ruangan mengintip data ruangan lain.

Berikut adalah analisis 4 Role Utama yang paling ideal untuk sistem LinenFlow, lengkap dengan fungsi dan detail permission-nya.

1. Super Admin (IT / Sistem)
Persona: Staf IT RS atau Vendor Developer. Fungsi: Menjaga "kesehatan" sistem, bukan operasional linen harian.

Tanggung Jawab:

Setup awal aplikasi.

Manajemen User (Tambah pegawai baru, Reset password).

Assignment Role (Siapa jadi apa).

Hak Akses (Permissions):

manage_users: Create, Read, Update, Delete (CRUD) data user.

assign_roles: Memberikan role ke user.

view_system_logs: Melihat siapa melakukan apa (Audit Trail).

Note: Sebaiknya Super Admin TIDAK ikut campur input transaksi harian agar data tetap murni operasional.

2. Laundry Manager (Kepala Instalasi)
Persona: Kepala Unit Laundry / Manajer Operasional. Fungsi: Pengambil keputusan, pemegang kendali stok, dan auditor.

Tanggung Jawab:

Mengatur Master Data (Jenis Linen, Daftar Ruangan, Standar Par Stock).

Melakukan Stock Opname (Penyesuaian stok jika ada selisih).

Approval pemusnahan barang (Afkir) untuk linen rusak.

Menganalisa laporan kehilangan/keuangan.

Hak Akses (Permissions):

manage_master_data: CRUD Linen & Rooms.

create_adjustment: Melakukan koreksi stok manual (kewenangan tinggi).

approve_disposal: Menyetujui linen dibuang/dihapus dari aset.

view_financial_reports: Melihat laporan rugi/laba aset.

view_all_stats: Melihat dashboard global semua ruangan.

3. Laundry Operator (Staf Operasional)
Persona: Staf yang bekerja di gudang laundry, mencuci, dan melipat. Fungsi: Ujung tombak input data harian. User yang paling sering login.

Tanggung Jawab:

Mencatat linen kotor masuk (Infection/Non-Infection).

Mencatat proses cuci (Start/Finish).

Mencatat distribusi linen bersih ke ruangan.

Hak Akses (Permissions):

create_transaction_in: Input linen kotor.

create_transaction_out: Input kirim linen bersih.

create_transaction_process: Update status cuci.

view_own_dashboard: Melihat stok gudang laundry saat ini.

Restriction: TIDAK BISA edit Master Data, TIDAK BISA hapus transaksi yang sudah disimpan (harus lapor Manager kalau salah input), TIDAK BISA lihat nilai uang/harga aset.

4. Head Nurse (Kepala Ruangan)
Persona: Kepala Perawat di Ruang Rawat Inap (misal: KaRu Mawar). Fungsi: Konsumen linen. Memastikan stok di ruangannya cukup untuk pasien.

Tanggung Jawab:

Memantau stok real-time di ruangannya sendiri.

(Opsional) Melakukan Request Order jika stok menipis mendadak.

Validasi penerimaan (Tanda terima digital saat linen bersih datang).

Hak Akses (Permissions):

view_room_stock: Hanya bisa melihat stok ruangannya sendiri (Scope Data).

create_request: Membuat permintaan tambahan.

confirm_receipt: Mengklik tombol "Diterima" saat barang datang.

// RoomStockController.php
public function index()
{
    $user = auth()->user();

    // Jika user adalah Kepala Ruangan, filter query
    if ($user->hasRole('head_nurse')) {
        // Asumsi user punya relasi ke room_id
        $stocks = RoomStock::where('room_id', $user->room_id)->get();

        // Manager bisa lihat semua
        $stocks = RoomStock::all();
    }

}

Centralized Control: Kalau mau ganti urutan menu, tinggal edit config/navigation.php. Nggak perlu acak-acak HTML.

Secure: Menu benar-benar hilang dari HTML (bukan cuma di-hide CSS) kalau user nggak punya hak akses.

Flexible: Admin bisa mengatur akses via fitur "Role Management" (Assign Permission ke Role), dan sidebar akan otomatis menyesuaikan diri tanpa kamu koding ulang.

Selanjutnya terkait menu admin,
Sebenarnya, ini adalah pendekatan yang sangat umum di dunia Enterprise Software. Biasanya peran ini disebut "Auditor" atau "Observer", tapi sering kali peran Super Admin juga butuh kemampuan ini untuk troubleshooting.

Bayangkan skenario ini: User di lapangan komplain "Error nih nggak bisa input!". Sebagai Admin, kamu harus bisa buka halaman yang sama untuk melihat apa yang mereka lihat, tapi tanpa risiko kamu nggak sengaja ngubah data stok.

Granular Permissions: Kita harus memecah permission menjadi lebih detail (Atomic).
